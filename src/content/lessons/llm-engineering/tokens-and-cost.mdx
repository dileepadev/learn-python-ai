Everything in this module has a price, and almost all of it is input tokens you sent more than
once. This lesson is about measuring that and then reducing it — in the order that costs you
nothing first.

## Counting tokens

Ask the API. Token counts are model-specific, and the endpoint is free:

```python
import anthropic

client = anthropic.Anthropic()

count = client.messages.count_tokens(
    model="claude-opus-5",
    system=SYSTEM_PROMPT,
    messages=[{"role": "user", "content": document}],
)
print(count.input_tokens)
```

<Callout type="warning">
Do not use `tiktoken`. It is OpenAI's tokeniser and it undercounts Claude tokens by roughly
15-20% on ordinary prose, and by considerably more on code or non-English text. An estimate from
the wrong tokeniser is not a rough estimate, it is a wrong one — and it is wrong in the direction
that makes you overrun a context window in production.
</Callout>

A rough local estimate is fine for a sanity check, as long as you know it is rough:

<Run id="llm-cost-1" code={`def rough_tokens(text):

## The usage block

<Run id="llm-cost-2" code={`from types import SimpleNamespace

## How caching works

The cache is a **prefix match**. The request is rendered in a fixed order, and a breakpoint says
"everything up to here is cacheable":

```text
tools  ->  system  ->  messages
```

Any byte that changes anywhere in that prefix invalidates the cache from that point on. So the
architecture is simple to state and easy to get wrong: **stable content first, volatile content
last.**

<Run id="llm-cost-3" code={`import hashlib

def prefix_key(*parts):
    """The cache is keyed on the exact bytes of the prefix."""
    return hashlib.sha256("\\u0000".join(parts).encode("utf-8")).hexdigest()[:12]

TOOLS = "[search_docs, read_doc]"
SYSTEM = "You are a documentation assistant. Answer only from the provided context."

cache = {}

def call(tools, system, question):
    key = prefix_key(tools, system)
    hit = key in cache
    cache[key] = True
    return "HIT " if hit else "MISS"

print(call(TOOLS, SYSTEM, "What is chunking?"), "first call")
print(call(TOOLS, SYSTEM, "What about overlap?"), "same prefix, different question")
print(call(TOOLS, SYSTEM, "And embeddings?"), "same prefix again")
print()
print(call(TOOLS, SYSTEM + " Today is 2026-03-01.", "What is chunking?"), "<- system prompt changed")
print(call("[search_docs, read_doc, delete_doc]", SYSTEM, "What is chunking?"), "<- tool list changed")`} />

On your own machine, the simplest form caches the last cacheable block automatically:

```python
response = client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,
    cache_control={"type": "ephemeral"},        # cache the last cacheable block
    system=LARGE_STABLE_SYSTEM_PROMPT,
    messages=[{"role": "user", "content": question}],
)
```

Or place breakpoints yourself, when you want the boundary in a specific spot:

```python
response = client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,
    system=[
        {"type": "text", "text": STABLE_INSTRUCTIONS},
        {"type": "text", "text": THE_WHOLE_HANDBOOK,
         "cache_control": {"type": "ephemeral", "ttl": "1h"}},
    ],
    messages=[{"role": "user", "content": question}],
)
```

At most four breakpoints per request. The default time to live is five minutes, refreshed on each
hit; `"1h"` is available when your traffic is spikier than that.

<Callout type="warning">
There is a minimum cacheable prefix — between about 512 and 4,096 tokens depending on the model.
Below it, nothing is cached and nothing tells you so: `cache_read_input_tokens` simply stays at
zero. Caching a 200-token system prompt does nothing at all.
</Callout>

## Silent invalidators

This is where hit rates actually go to die:

<Run id="llm-cost-4" code={`import json
from datetime import datetime

INVALIDATORS = [

    print(f"- {problem}\\n    {why}\\n    fix: {fix}")`} />

<Run id="llm-cost-5" code={`import json, hashlib

def render_prefix(tools, system):
    return json.dumps({"tools": tools, "system": system}, sort_keys=True)

def fingerprint(prefix):
    return hashlib.sha256(prefix.encode("utf-8")).hexdigest()[:10]

tools_a = [{"name": "search"}, {"name": "read"}]
tools_b = [{"name": "read"}, {"name": "search"}]        # same set, different order

print("sorted by name:")
for tools in (tools_a, tools_b):
    ordered = sorted(tools, key=lambda t: t["name"])
    print("  ", fingerprint(render_prefix(ordered, "stable system prompt")))

print("as given:")
for tools in (tools_a, tools_b):
    print("  ", fingerprint(render_prefix(tools, "stable system prompt")))`} />

Two identical tool sets, two different cache keys — unless you sort them. Verify in production
rather than assuming:

<Run id="llm-cost-6" code={`from types import SimpleNamespace

def cache_health(usages):
    reads = sum(u.cache_read_input_tokens for u in usages)
    writes = sum(u.cache_creation_input_tokens for u in usages)
    fresh = sum(u.input_tokens for u in usages)
    total = reads + writes + fresh
    return {
        "hit_rate": round(reads / total, 3) if total else 0.0,
        "read": reads, "written": writes, "uncached": fresh,
    }

healthy = [SimpleNamespace(input_tokens=150, output_tokens=200,
                           cache_creation_input_tokens=18_000 if i == 0 else 0,
                           cache_read_input_tokens=0 if i == 0 else 18_000)
           for i in range(10)]

broken = [SimpleNamespace(input_tokens=150, output_tokens=200,
                          cache_creation_input_tokens=18_000,
                          cache_read_input_tokens=0)
          for _ in range(10)]

print("healthy:", cache_health(healthy))
print("broken: ", cache_health(broken))
print()
print("A hit rate near zero with repeated writes means the prefix changes every request.")`} />

That second pattern — writing the cache on every single call and never reading it — costs you
*more* than not caching at all, because writes are 1.25x.

<Callout type="ai" title="Why this matters for AI">
Caching is the one lever that is genuinely free: the answer does not change, only the bill. A RAG
system with a large stable system prompt, or an agent resending a growing history, is exactly the
shape that benefits most — and those are the systems where the prefix is easiest to break by
accident. Check `cache_read_input_tokens` on real traffic. If it is zero, something in your
prefix moves, and finding it is usually worth more than every other optimisation combined.
</Callout>

## The order of the levers

<Run id="llm-cost-7" code={`LEVERS = [
    ("free", "Prompt caching", "Stable prefix, volatile content last. No quality change."),
    ("free", "Input hygiene", "Stop resending what the model does not need. No quality change."),
    ("free", "Output hygiene", "Ask for shorter answers. Output is ~5x the input rate."),
    ("free", "Batch API", "50% off for anything not latency-sensitive."),
    ("trade", "Lower effort", "Measurably cheaper; measure whether quality holds on your traffic."),
    ("trade", "A smaller model", "Much cheaper; needs an eval to justify per route."),
    ("trade", "Fewer agent rounds", "Cheaper, and sometimes worse. Bound it either way."),
]

print(f"{'kind':>6}  {'lever':<18} {'note'}")
for kind, lever, note in LEVERS:
    print(f"{kind:>6}  {lever:<18} {note}")

print()
print("Do every free lever before trading any quality — and judge cost per completed task,")
print("not per request. A cheaper call that needs three attempts is not cheaper.")`} />

The batch path is worth knowing, because half price for no quality change is unusual:

```python
batch = client.messages.batches.create(requests=[
    {"custom_id": "q-1", "params": {"model": "claude-opus-5", "max_tokens": 1024,
                                    "messages": [{"role": "user", "content": "..."}]}},
    {"custom_id": "q-2", "params": {...}},
])

while client.messages.batches.retrieve(batch.id).processing_status != "ended":
    time.sleep(30)

for entry in client.messages.batches.results(batch.id):
    if entry.result.type == "succeeded":
        store(entry.custom_id, entry.result.message)
```

<Callout type="warning">
Batch results arrive in **any order**. Key them by `custom_id` — never by position. Nightly
evaluations, backfills and bulk classification are all natural batch workloads.
</Callout>

    while n < 10_000:
        uncached = n * 1.0

## Recap

- Count tokens with `client.messages.count_tokens`, never with `tiktoken`.
- `usage` has four fields: uncached input, output, cache writes (~1.25x) and cache reads (~0.1x).
- The cache is a prefix match over `tools -> system -> messages`. Stable content first, volatile
  content after the last breakpoint. At most four breakpoints, and a minimum prefix size below
  which nothing caches silently.
- Timestamps, UUIDs, unsorted JSON and reordered tool lists are the invalidators to hunt for; a
  hit rate near zero with repeated writes costs more than no cache at all.
- Do the free levers — caching, input and output hygiene, batch — before trading any quality, and
  judge cost per completed task.
