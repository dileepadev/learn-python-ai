between two Tuesdays — and, more usefully, numbers that say *which stage* to fix.

## Retrieval metrics

<Run id="rag-eval-2" code={`def recall_at_k(retrieved, relevant, k):
    """Of the chunks that should have been found, how many were in the top k?"""
    if not relevant:
        return None                      # undefined when nothing is relevant
    found = set(retrieved[:k]) & set(relevant)
    return len(found) / len(relevant)

def precision_at_k(retrieved, relevant, k):
    """Of the top k, how many were actually relevant?"""
    if k == 0:
        return 0.0
    return len(set(retrieved[:k]) & set(relevant)) / k

def reciprocal_rank(retrieved, relevant):
    """1/rank of the first relevant result, or 0 if none was found."""
    for rank, identifier in enumerate(retrieved, start=1):
        if identifier in relevant:
            return 1.0 / rank
    return 0.0

retrieved = ["c7", "c1", "c9", "c5", "c2"]
relevant = ["c1", "c5"]

print("retrieved:", retrieved)
print("relevant: ", relevant)
print()
for k in [1, 3, 5]:
    print(f"recall@{k}    {recall_at_k(retrieved, relevant, k):.3f}"
          f"    precision@{k} {precision_at_k(retrieved, relevant, k):.3f}")
print()
print(f"reciprocal rank {reciprocal_rank(retrieved, relevant):.3f}  "
      f"(first relevant is at position 2)")`} />

The three answer different questions, and confusing them is common:

- **Recall@k** — did retrieval find the answer at all? This is the ceiling on everything after it.
- **Precision@k** — how much of what you retrieved was worth sending? This is your context budget.
- **MRR** — how near the top was the first good one? This is what re-ranking improves.

    "reranked":  [["c1", "c7", "c9"], ["c2", "c8", "c4"], ["c3", "c9", "c7"]],

## nDCG

When some results are more relevant than others, a binary label is too coarse. nDCG weights by
graded relevance and discounts by position:

<Run id="rag-eval-4" code={`import math

def dcg(relevances):
    return sum(relevance / math.log2(rank + 1) for rank, relevance in enumerate(relevances, start=1))

def ndcg_at_k(retrieved, graded, k=5):
    """graded: {chunk_id: relevance}, where 0 means irrelevant."""
    actual = [graded.get(identifier, 0) for identifier in retrieved[:k]]
    ideal = sorted(graded.values(), reverse=True)[:k]
    best = dcg(ideal)
    return dcg(actual) / best if best else 0.0

graded = {"c1": 3, "c5": 2, "c2": 1}          # 3 = perfect, 1 = tangential

for name, ranking in [
    ("perfect order", ["c1", "c5", "c2", "c9", "c7"]),
    ("good but shuffled", ["c5", "c1", "c9", "c2", "c7"]),
    ("best result last", ["c9", "c7", "c2", "c5", "c1"]),
    ("nothing relevant", ["c9", "c7", "c8", "c6", "c4"]),
]:
    print(f"{name:20} nDCG@5 {ndcg_at_k(ranking, graded):.4f}")`} />

The discount is logarithmic, so moving a result from position 1 to 2 costs far more than moving it
from 9 to 10 — which matches how people read a list.

## End-to-end metrics

Retrieval quality is a means. What you ship is the answer:

<Run id="rag-eval-5" code={`import re

REFUSAL = "I don't know based on the provided documentation."

def evaluate_answer(answer, supplied_ids, example):
    cited = set(re.findall(r"\\[([a-zA-Z0-9_]+)\\]", answer))
    refused = answer.strip() == REFUSAL
    unsupported = cited - set(supplied_ids)

    return {
        "refused": refused,
        "refused_correctly": refused and not example["answerable"],
        "refused_wrongly": refused and example["answerable"],
        "answered_unanswerable": not refused and not example["answerable"],
        "cited_something": bool(cited),
        "citations_supported": not unsupported,
        "cited_relevant": bool(cited & set(example["relevant"])),
    }

cases = [
    ("Use 10 to 20 percent [c1].", ["c1", "c2"],
     {"answerable": True, "relevant": ["c1"]}, "grounded and correct"),
    ("Use 10 to 20 percent.", ["c1"],
     {"answerable": True, "relevant": ["c1"]}, "right, but uncited"),
    ("Store as float16 [c9].", ["c1", "c2"],
     {"answerable": True, "relevant": ["c2"]}, "fabricated citation"),
    (REFUSAL, [], {"answerable": False, "relevant": []}, "correctly refused"),
    ("The weather is sunny [c1].", ["c1"],
     {"answerable": False, "relevant": []}, "answered the unanswerable"),
]

for answer, supplied, example, label in cases:
    result = evaluate_answer(answer, supplied, example)
    flags = [name for name, value in result.items() if value]
    print(f"{label:26} {flags}")`} />

Four numbers are worth reporting from that, and they are not interchangeable:

<Run id="rag-eval-6" code={`METRICS = [
    ("Answer rate", "answered / all", "How often the system produces an answer at all."),
    ("Refusal precision", "correct refusals / all refusals",
     "When it refuses, is it right to? Low means it is refusing answerable questions."),
    ("Refusal recall", "correct refusals / unanswerable questions",
     "Of the questions it should refuse, how many does it? Low means it invents answers."),
    ("Citation support", "answers with only supplied ids / cited answers",
     "Mechanically checkable. Should be 1.0, and anything less is fabrication."),
    ("Groundedness", "claims supported by the cited chunk / claims",
     "Needs a judge or a human. The expensive one, and the one that matters most."),
]

for name, formula, why in METRICS:
    print(f"{name}\\n  {formula}\\n  {why}\\n")`} />

<Callout type="warning">
Answer rate and refusal recall trade against each other, and a single "accuracy" number hides the
trade completely. A system that answers everything scores well on answerable questions and
terribly on the rest; one that refuses everything does the reverse. Report both, always.
</Callout>

## Ablation

When end-to-end quality drops, the useful question is *where*. Ablate:

<Run id="rag-eval-7" code={`def diagnose(example, retrieved, answer, supplied_ids):
    """Walk the stages in order and stop at the first that failed."""
    relevant = set(example["relevant"])

    if example["answerable"] and relevant and not (set(retrieved) & relevant):
        return "retrieval", "the answer was never retrieved — chunking or embedding"

    if example["answerable"] and relevant and not (set(supplied_ids) & relevant):
        return "selection", "retrieved but not selected — score floor or budget too tight"

    if answer.strip() == REFUSAL and example["answerable"]:
        return "generation", "the context contained the answer and the model refused"

    cited = set(re.findall(r"\\[([a-zA-Z0-9_]+)\\]", answer))
    if cited - set(supplied_ids):
        return "generation", "cited a chunk that was never supplied"

    if not example["answerable"] and answer.strip() != REFUSAL:
        return "generation", "answered a question the corpus cannot answer"

    return "ok", "answered from the supplied context"

import re
REFUSAL = "I don't know based on the provided documentation."

cases = [
    ({"answerable": True, "relevant": ["c1"]}, ["c7", "c9"], "Something [c7].", ["c7"]),
    ({"answerable": True, "relevant": ["c1"]}, ["c1", "c9"], REFUSAL, ["c9"]),
    ({"answerable": True, "relevant": ["c1"]}, ["c1"], REFUSAL, ["c1"]),
    ({"answerable": True, "relevant": ["c1"]}, ["c1"], "Use 10-20% [c1].", ["c1"]),
    ({"answerable": False, "relevant": []}, ["c9"], "It is sunny [c9].", ["c9"]),
]

for example, retrieved, answer, supplied in cases:
    stage, why = diagnose(example, retrieved, answer, supplied)
    print(f"{stage:11} {why}")`} />

<Callout type="ai" title="Why this matters for AI">
That function is the most useful thing in the module. Without it, every bad answer looks like a
model problem, and teams spend weeks on prompts when the answer was never retrieved. With it, a
failing evaluation run produces a histogram over stages — and the histogram tells you whether to
work on chunking, on the floor, or on the prompt. Measure the stage, not just the outcome.
</Callout>

## LLM as judge

Groundedness — "is this claim actually supported by the cited passage?" — needs a reader. A model
can be that reader, with caveats:

<Run id="rag-eval-8" code={`JUDGE_PROMPT = """You are checking whether an answer is supported by its source.

<passage>
{passage}
</passage>

<claim>{claim}</claim>

Reply with exactly one word:
  supported   - the passage states this, or directly implies it
  contradicted - the passage states the opposite
  unsupported - the passage neither states nor implies it
"""

CAVEATS = [
    "A judge agrees with itself far more than with a human. Measure that agreement "
    "on a sample you labelled by hand, before trusting any number it produces.",
    "Judges prefer longer, more confident answers, and prefer answers from the same "
    "model family. Both biases move scores without moving quality.",
    "Ask for a label from a fixed set, not a score from 1 to 10. Labels are far more "
    "stable between runs.",
    "Judge one claim against one passage. A whole-answer verdict hides which sentence "
    "was the problem.",
]

print(JUDGE_PROMPT.format(passage="Use 10 to 20 percent overlap.", claim="Use 15 percent overlap."))
print("Caveats:")
for caveat in CAVEATS:
    print(f"  - {caveat}")`} />

Module 8 takes this further, including how to calibrate a judge against human labels. For now the
important part is the ordering: **the mechanical checks come first.** Citation support costs
nothing and catches the worst failures; reach for a judge only for what mechanics cannot see.

## Recap

- Build a small, deliberate evaluation set, labelled with the relevant chunk ids, and include
  questions that should be refused.
- **Recall@k** is the ceiling, **precision@k** is your context budget, **MRR** is what re-ranking
  moves, and **nDCG** handles graded relevance with a positional discount.
- End to end, report answer rate, refusal precision and recall, citation support and groundedness
  — never one blended "accuracy".
- Ablate by stage: never retrieved, retrieved but not selected, selected but refused, or cited
  something that was not supplied.
- Do the mechanical checks first; a judge is for what mechanics cannot see, and needs calibrating
  against human labels before you trust it.
