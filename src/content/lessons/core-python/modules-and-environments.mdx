A script becomes software when it stops being one file. Modules are how Python splits code up,
and environments are how you make sure the code that ran on your laptop runs on the machine that
trains the model.

## Importing

<Run id="cp-mod-1" code={`import math
print(math.sqrt(144), math.pi)

from statistics import mean, median          # pull names into this file
print(mean([0.71, 0.88, 0.93]), median([0.71, 0.88, 0.93]))

import json as j                             # rename on import
print(j.dumps({"model": "claude-opus-5"}))

from collections import Counter              # the form you will use most
print(Counter("mississippi").most_common(2))`} />

`import x` keeps the module's namespace, so you write `x.thing` and a reader knows where `thing`
came from. `from x import thing` is shorter at every use site. Prefer the second for a handful of
well-known names, the first when the module name adds clarity.

<Callout type="warning">
Never write `from module import *`. It drops every public name into your file at once, so a
reader cannot tell what came from where — and a later import can silently replace a name you
were relying on.
</Callout>

## Your own modules

A module is just a `.py` file. Python's virtual filesystem is available here, so you can write
one and import it in the same program:

<Run id="cp-mod-2" code={`from pathlib import Path
import sys

Path("metrics.py").write_text('''
"""Scoring helpers."""

THRESHOLD = 0.85

def accuracy(correct, total):
    return correct / total

def passes(score):
    return score >= THRESHOLD
''')

sys.path.insert(0, ".")          # make the current directory importable

import metrics

print(metrics.THRESHOLD)
print(metrics.accuracy(43, 50))
print(metrics.passes(0.86), metrics.passes(0.5))
print(metrics.__doc__.strip())`} />

Everything defined at the top level of that file — constants, functions, classes — becomes an
attribute of the module object.

## A module runs once

The first `import` executes the file top to bottom. Every later import of the same name reuses
the module object already in `sys.modules`:

<Run id="cp-mod-3" code={`from pathlib import Path
import sys

Path("noisy.py").write_text('print("  noisy.py is being executed")\\n')
sys.path.insert(0, ".")

print("first import:")
import noisy

print("second import:")
import noisy          # nothing prints — it is already loaded

print("in sys.modules:", "noisy" in sys.modules)`} />

That is why import-time work is dangerous: a module that opens a connection or loads a 2 GB
checkpoint at the top level does it the moment anything imports it, including your test suite.

## The main check

A file can be imported *and* run directly. The difference is the `__name__` variable: it is
`"__main__"` when the file is the program, and the module's name when it has been imported.

<Run id="cp-mod-4" code={`from pathlib import Path
import sys

Path("tool.py").write_text('''
def clean(text):
    return " ".join(text.split()).lower()

print("  top level: __name__ is", __name__)

if __name__ == "__main__":
    print("  running as a script")
''')

sys.path.insert(0, ".")
import tool                       # imported, so __name__ is "tool"

print("here, __name__ is", __name__)
print(tool.clean("  RAGGED   text  "))`} />

Put everything a script *does* behind `if __name__ == "__main__":` and everything it *offers*
above the guard. Then the same file is both a command-line tool and an importable library.

## Packages

A package is a directory of modules. An `__init__.py` file makes it importable as one unit, and
is the natural place to decide what the package exposes:

<Run id="cp-mod-5" code={`from pathlib import Path
import sys

Path("rag").mkdir(exist_ok=True)
Path("rag/chunking.py").write_text('''
def split(text, size=20):
    words = text.split()
    return [" ".join(words[i:i + size]) for i in range(0, len(words), size)]
''')
Path("rag/scoring.py").write_text('''
def overlap(a, b):
    a_words, b_words = set(a.split()), set(b.split())
    return len(a_words & b_words) / len(a_words | b_words)
''')
Path("rag/__init__.py").write_text('''
"""A tiny retrieval package."""
from .chunking import split
from .scoring import overlap

__all__ = ["split", "overlap"]
''')

sys.path.insert(0, ".")

import rag
print(rag.split("one two three four five six", size=2))
print(round(rag.overlap("cat sat mat", "cat sat rug"), 3))

from rag.scoring import overlap   # reach into a submodule directly
print(round(overlap("a b", "a b"), 3))`} />

The leading dot in `from .chunking import split` is a **relative import** — "the `chunking`
module next to me". Use relative imports inside a package and absolute imports everywhere else.

## How Python finds a module

`sys.path` is searched in order, and the first match wins:

<Run id="cp-mod-6" code={`import sys, json, statistics

for entry in sys.path[:5]:
    print(repr(entry))

print()
print("json lives at:      ", json.__file__)
print("statistics lives at:", statistics.__file__)`} />

Because the directory of your script comes first, a file of your own called `random.py` or
`json.py` shadows the standard library module of that name — and the error it produces points
somewhere else entirely:

<Run id="cp-mod-7" code={`from pathlib import Path
from importlib.machinery import PathFinder
import sys

Path("random.py").write_text("# my own notes about randomness\\n")
sys.path.insert(0, ".")

# What would "import random" actually load from here?
print("random ->", PathFinder().find_spec("random", sys.path).origin)

# ...and what it should have been, with our directory taken out of the search:
clean_path = [entry for entry in sys.path if entry != "."]
print("really  ->", PathFinder().find_spec("random", clean_path).origin)`} />

A program that started from that directory would import the empty file, and every later
`random.randint(...)` would fail with `AttributeError: module 'random' has no attribute
'randint'` — pointing at a line that has nothing wrong with it.

<Callout type="warning">
If an import of a standard library module suddenly fails with `AttributeError` or
`ImportError: cannot import name`, look for a file of your own with that name in the directory
you are running from. It is almost always that.
</Callout>

## Virtual environments

Installing packages system-wide means every project shares one set of versions, and two projects
eventually want different ones. A virtual environment is a private directory of packages for one
project.

These commands run on your own machine, not in this page:

```bash
python -m venv .venv           # create it
source .venv/bin/activate      # activate it (Linux/macOS)
.venv\Scripts\activate         # activate it (Windows)

pip install numpy pandas scikit-learn
pip list                       # what is installed
deactivate                     # leave it
```

Once active, `python` and `pip` refer to the environment's copies. `.venv/` is generated, so it
belongs in `.gitignore`, never in a commit.

## Pinning what you installed

Recording versions is what makes a run repeatable:

```bash
pip freeze > requirements.txt        # exact versions of everything installed
pip install -r requirements.txt      # recreate that environment elsewhere
```

A modern project declares its dependencies in `pyproject.toml` instead, separating what you
*depend on* from what happened to get installed:

```toml
[project]
name = "rag-service"
requires-python = ">=3.11"
dependencies = [
    "anthropic>=0.40,<1.0",
    "numpy>=2.0",
    "pydantic>=2.7",
]

[project.optional-dependencies]
dev = ["pytest>=8.0", "mypy>=1.10"]
```

<Callout type="ai" title="Why this matters for AI">
An evaluation result is only meaningful alongside the environment that produced it. A minor
version bump in a tokeniser changes how text is split; a change in scikit-learn's default solver
changes a model's coefficients; an SDK release changes a default `max_tokens`. "It scored 0.91"
means nothing without a pinned environment. Pin your dependencies, commit the lock file, and
record versions next to metrics.
</Callout>

## Recap

- `import x` keeps the namespace; `from x import y` is shorter. Never `import *`.
- A module is a `.py` file; its top-level names become attributes. A package is a directory with
  an `__init__.py` that decides what the package exposes.
- A module's body runs **once**, on first import — so avoid expensive work at import time.
- `__name__` is `"__main__"` only when the file is the program. Guard script behaviour with it.
- `sys.path` is searched in order and your own directory comes first, so never name a file after
  a standard library module.
- A virtual environment isolates a project's packages; pinned versions in `requirements.txt` or
  `pyproject.toml` are what make a result reproducible.
