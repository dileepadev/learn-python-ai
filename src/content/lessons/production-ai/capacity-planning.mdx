## Little's law

The one piece of queueing theory worth memorising: **concurrency = throughput × latency**.

<Run id="prod-cap-4" code={`def concurrency_needed(requests_per_second, seconds_per_request):
    return requests_per_second * seconds_per_request

print(f"{'req/s':>7} {'latency':>9} {'in flight':>11}")
for rate, latency in [(1, 2.0), (5, 2.0), (5, 8.0), (20, 2.0), (50, 3.5)]:
    print(f"{rate:>7} {latency:>8.1f}s {concurrency_needed(rate, latency):>11.0f}")

print()
peak_rate, p95 = 12, 4.0
needed = concurrency_needed(peak_rate, p95)
print(f"At {peak_rate} requests/second with a p95 of {p95}s you need {needed:.0f} in flight.")
print("Size for the p95, not the median — the slow requests are the ones occupying slots.")`} />

It runs backwards too, which is usually the more useful direction:

<Run id="prod-cap-5" code={`def throughput(concurrency, seconds_per_request):
    return concurrency / seconds_per_request

limit = 20            # concurrency your rate limit allows
print(f"with a concurrency limit of {limit}:")
for latency in [0.5, 2.0, 4.0, 10.0]:
    rate = throughput(limit, latency)
    print(f"  latency {latency:>5.1f}s -> {rate:>6.1f} req/s  ({rate * 3600:>8,.0f} per hour)")

print()
print("Latency and throughput are the same constraint seen twice. Halving latency")
print("doubles throughput at the same concurrency — and costs nothing extra.")`} />

<Callout type="warning">
A queue in front of a saturated service does not add capacity; it converts rejection into
latency. If arrivals exceed `concurrency / latency` for any sustained period the queue grows
without bound, and users wait longer and longer for a request that will eventually time out
anyway. Shed load, or add concurrency.
</Callout>

## A cost model

<Run id="prod-cap-6" code={`PRICING = {
    "claude-opus-5":    {"input": 5.00,  "output": 25.00},
    "claude-sonnet-5":  {"input": 2.00,  "output": 10.00},
    "claude-haiku-4-5": {"input": 1.00,  "output": 5.00},
}
CACHE_WRITE, CACHE_READ = 1.25, 0.10

def request_cost(model, *, fresh_input, cached_input, output, cache_writes=0):
    rates = PRICING[model]
    return (
        fresh_input * rates["input"]
        + cached_input * rates["input"] * CACHE_READ
        + cache_writes * rates["input"] * CACHE_WRITE
        + output * rates["output"]
    ) / 1_000_000

# One RAG answer: a big stable system prompt, retrieved context, a short reply.
shape = {"fresh_input": 1_200, "cached_input": 6_000, "output": 180}

print(f"{'model':<18} {'per request':>12} {'per 1k users/day':>18} {'per month':>12}")
for model in PRICING:
    one = request_cost(model, **shape)
    daily = one * 1_000 * 8          # 1000 users, 8 requests a day each
    print(f"{model:<18} {one:>12.5f} {daily:>18.2f} {daily * 30:>12.2f}")`} />

<Run id="prod-cap-7" code={`PRICING = {"claude-opus-5": {"input": 5.00, "output": 25.00}}

def cost(fresh, cached, output, writes=0):
    r = PRICING["claude-opus-5"]
    return (fresh * r["input"] + cached * r["input"] * 0.10
            + writes * r["input"] * 1.25 + output * r["output"]) / 1_000_000

monthly_requests = 1_000 * 8 * 30

scenarios = [
    ("no caching", cost(7_200, 0, 180)),
    ("caching, 90% hit rate", 0.9 * cost(1_200, 6_000, 180) + 0.1 * cost(1_200, 0, 180, writes=6_000)),
    ("caching + shorter answers", 0.9 * cost(1_200, 6_000, 90) + 0.1 * cost(1_200, 0, 90, writes=6_000)),
    ("...and half the retrieved context", 0.9 * cost(1_200, 3_000, 90) + 0.1 * cost(1_200, 0, 90, writes=3_000)),
]

baseline = scenarios[0][1] * monthly_requests
print(f"{'scenario':<34} {'per request':>12} {'per month':>11} {'saving':>8}")
for name, per_request in scenarios:
    monthly = per_request * monthly_requests
    print(f"{name:<34} {per_request:>12.5f} {monthly:>10.2f} {1 - monthly / baseline:>8.0%}")`} />

Three changes, none of which alters the answer: cache the stable prefix, ask for a shorter reply,
and stop sending context the model did not use. Together they take roughly two thirds off the
bill.

<Callout type="ai" title="Why this matters for AI">
Do this arithmetic *before* building. A per-request cost of half a cent is invisible in
development and is $120,000 a year at a million requests a month — and the levers that fix it,
from module 6, are structural: what sits in the cacheable prefix, how much context you retrieve,
how long the answer is. Retrofitting them means changing the prompt, which means re-running every
evaluation. Ten minutes with this spreadsheet at design time is worth a quarter of engineering
later.
</Callout>

## Check it against the limits

<Run id="prod-cap-8" code={`def plan(*, peak_requests_per_second, p95_seconds,
         input_tokens, output_tokens,
         request_limit_per_minute, token_limit_per_minute, headroom=0.7):
    concurrency = peak_requests_per_second * p95_seconds
    requests_per_minute = peak_requests_per_second * 60
    tokens_per_minute = requests_per_minute * (input_tokens + output_tokens)

    return {
        "concurrency": round(concurrency),
        "requests_per_minute": round(requests_per_minute),
        "tokens_per_minute": round(tokens_per_minute),
        "request_headroom": requests_per_minute / (request_limit_per_minute * headroom),
        "token_headroom": tokens_per_minute / (token_limit_per_minute * headroom),
    }

result = plan(
    peak_requests_per_second=12, p95_seconds=4.0,
    input_tokens=7_200, output_tokens=180,
    request_limit_per_minute=4_000, token_limit_per_minute=400_000,
)

print(f"concurrency needed:   {result['concurrency']}")
print(f"requests per minute:  {result['requests_per_minute']:,}")
print(f"tokens per minute:    {result['tokens_per_minute']:,}")
print()
for name in ["request_headroom", "token_headroom"]:
    usage = result[name]
    verdict = "fits" if usage <= 1.0 else f"OVER by {usage - 1:.0%}"
    print(f"{name:<20} {usage:>6.2f} of the usable budget   {verdict}")

print()
print("The token limit binds first, as it usually does — one long request can")
print("consume a minute's request budget many times over in tokens.")`} />

<Callout type="tip">
Plan against 70% of your published limit, not 100%. Traffic is bursty, retries add load exactly
when you are already at the limit, and a deploy briefly doubles your client count. A plan that
fits at 100% does not fit.
</Callout>

## The whole plan on one page

<Run id="prod-cap-9" code={`def capacity_plan(*, daily_active_users, requests_per_user_per_day, peak_multiplier,
                  p95_seconds, input_tokens, output_tokens, cache_hit_rate,
                  input_rate, output_rate):
    daily_requests = daily_active_users * requests_per_user_per_day
    average_rate = daily_requests / 86_400
    peak_rate = average_rate * peak_multiplier

    cached = input_tokens * cache_hit_rate
    fresh = input_tokens - cached
    per_request = (fresh * input_rate + cached * input_rate * 0.10
                   + output_tokens * output_rate) / 1_000_000

    return {
        "daily requests": f"{daily_requests:,.0f}",
        "average rate": f"{average_rate:.2f}/s",
        "peak rate": f"{peak_rate:.2f}/s",
        "concurrency at peak": f"{peak_rate * p95_seconds:.0f}",
        "tokens per minute at peak": f"{peak_rate * 60 * (input_tokens + output_tokens):,.0f}",
        "cost per request": f"\\u0024{per_request:.5f}",
        "cost per user per month": f"\\u0024{per_request * requests_per_user_per_day * 30:.2f}",
        "cost per month": f"\\u0024{per_request * daily_requests * 30:,.2f}",
    }

for label, users in [("pilot", 200), ("launch", 5_000), ("a good year", 100_000)]:
    print(f"--- {label}: {users:,} daily active users")
    for key, value in capacity_plan(
        daily_active_users=users, requests_per_user_per_day=8, peak_multiplier=4,
        p95_seconds=4.0, input_tokens=7_200, output_tokens=180, cache_hit_rate=0.85,
        input_rate=5.00, output_rate=25.00,
    ).items():
        print(f"    {key:<28} {value}")
    print()`} />

Three numbers change the shape of the whole plan: the peak multiplier (traffic is never flat), the
cache hit rate (from module 6), and the p95 (which sets concurrency). Everything else follows.

## Recap

- Report latency as percentiles and split time-to-first-token from total; the mean of an AI
  workload describes nobody.
- **Concurrency = throughput × latency.** Size for the p95, and read it backwards to get the rate
  a concurrency limit allows.
- A queue does not add capacity; it converts rejection into unbounded latency.
- Build the cost model before building the system: caching, answer length and retrieved context
  are structural levers, and retrofitting them means re-running every evaluation.
- Check requests per minute *and* tokens per minute against your limits, at about 70% of them.
- Three numbers shape the plan: the peak multiplier, the cache hit rate and the p95.
